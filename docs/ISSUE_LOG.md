# 🐛 Chaos-Drop 개발 이슈 관리 문서 (Issue Log)

이 문서는 `chaos-drop` 프로젝트 개발 중 발생한 핵심 기술적 이슈와 해결 방안을 체계적으로 기록하고 관리하는 문서입니다.

---

## [ISSUE-01] 고주사율(High-Hz) 모니터에서의 물리 연산 속도 폭주 버그

### 1. 현상 (Symptoms)
*   일반 60Hz 모니터나 보급형 노트북에서는 정상적인 속도로 작동하던 구슬 경주 물리 엔진이 **144Hz, 165Hz, 240Hz 등의 게이밍 모니터**에서 구동 시 물리 속도가 **2.4배 ~ 4배까지 비정상적으로 폭주**하여 눈으로 궤적을 쫓을 수 없을 만큼 극도로 빠르게 흘러가는 현상.

### 2. 원인 분석 (Root Cause)
*   **프레임 비독립성 물리 루프 (Non-independent Frame Loop)**: 
    *   기존 게임 루프는 `requestAnimationFrame(animatePinball)`의 프레임마다 물리 연산(`ball.update()`, 장애물 충돌 검사 등)을 1회씩 정직하게 수행하도록 구현되어 있었습니다.
    *   `requestAnimationFrame`은 모니터 주사율에 맞춰 브라우저가 화면을 갱신할 때 호출되므로, 주사율이 높을수록 초당 물리 연산 횟수가 주사율 배수에 정비례하여 기하급수적으로 늘어나게 된 것입니다.
    *   *60Hz = 초당 60회 물리 연산 (정상)* vs *144Hz = 초당 144회 물리 연산 (2.4배 속행)*

### 3. 해결 방안 (Resolution)
*   **60FPS 제한 장치 (Frame Rate Limiter)** 도입:
    *   시스템 고해상도 타이머(`performance.now()` / `currentTime`)를 기반으로 밀리초 단위를 정밀 체크하여, 이전 프레임에서 정확히 **`16.67ms (1000ms / 60)`**가 경과했을 때만 물리 엔진과 드로잉을 전진시키는 루프 제한 기술을 도입했습니다.
    *   누적된 시간차의 잔여 오차(`elapsed % fpsInterval`)를 빼주는 정밀 보정 방식을 활용하여, 프레임 드랍이 있는 환경에서도 일정한 등속성을 유지합니다.

## [ISSUE-02] 동적 줌(Zoom) 배율 변경 시 화면 거친 흔들림(Jitter) 버그

### 1. 현상 (Symptoms)
*   PR #1(카메라 동적 줌 및 멀티 프레이밍) 적용 후, 구슬들의 밀집도에 따라 화면이 확대/축소될 때마다 **게임 보드판 전체가 좌우로 수십 픽셀씩 거칠게 튕기며 요동치는 현상**.
*   화면 털림으로 인해 구슬들이 마치 지그재그로 순간이동하는 듯한 불쾌한 잔상을 유발함.

### 2. 원인 분석 (Root Cause)
*   **줌 기준점(Pivot) 계산 오차**:
    *   화면 확대/축소(`ctx.scale`)의 피벗 좌표(`_zoomCX`)가 브라우저 창의 가로 절반(`window.innerWidth / 2`)으로 설계되어 있었습니다.
    *   그러나 이 게임은 좌측에 410px 크기의 **홀로그램 제어판**이 고정되어 있어, 실제 핀볼 게임판은 **오른쪽 영역에 편향되어 렌더링**(`GAME_X_OFFSET` 기준)됩니다.
    *   줌의 중심점과 실제 대상의 물리 중심이 수백 픽셀 어긋나 있어, 줌 배율이 변할 때마다 비대칭 횡이동 스케일이 적용되어 게임판이 좌우로 미친 듯이 털리게 된 현상입니다.

### 3. 해결 방안 (Resolution)
*   **게임판 실제 중심 정밀 얼라인먼트**:
    *   줌 피벗 가로 좌표(`_zoomCX`)를 실제 게임판의 정확한 렌더링 범위 중앙인 **`GAME_X_OFFSET + (GAME_VWIDTH / 2)`**로 완벽하게 조정했습니다.
    *   이에 따라 배율이 변해도 게임판이 좌우로 수평 이동하지 않고 중앙 기준 대칭으로 부드럽게 줌 인/아웃을 수행합니다.
    *   동시에 최대 줌 한도를 기존 `1.08x` ~ `1.10x`에서 최대 `1.03x` ~ `1.05x`로 보수적으로 제한하여 눈의 피로를 최소화했습니다.

## 📈 앞으로의 예방책 (Prevention)
1. **물리 독립성 원칙**: 향후 기믹이나 물리 상수를 추가할 때는 프레임 주사율에 영향을 받지 않도록 항상 60FPS 타이밍 델타에 속해 있는지 검증해야 합니다.
2. **좌표계 설계 분리**: 화면 배율 조정이나 트랜스레이션을 적용할 때는 UI 레이아웃 패널 오프셋(`GAME_X_OFFSET`)과 가상 좌표계(`GAME_VWIDTH`)의 분리를 명확히 지켜 피벗 오차를 차단합니다.

## [ISSUE-03] 모바일 뷰포트 스케일링에 따른 출구 런치패드(LaunchPad) 병목 버그

### 1. 현상 (Symptoms)
*   데스크탑에서는 문제없이 공이 빠져나가던 깔때기 하단 출구(Goal 입구)가, 모바일 기기(`BOARD_XSCALE < 1.0`) 접속 시 좁아져 구슬 여러 개가 출구 발판 3개 사이의 통로에 꽉 끼어 빠져나가지 못하고 무한히 갇히는 현상.

### 2. 원인 분석 (Root Cause)
*   물리 보드(`GAME_VWIDTH`) 전체 너비는 모바일 화면 폭에 맞춰 정상적으로 비례 축소(`BOARD_XSCALE`) 되었으나, 출구에 배치된 3개의 런치패드(LaunchPad) 폭이 기존의 하드코딩 픽셀 크기로 렌더링되면서 남은 여백 통로가 구슬 지름(`r=10`)보다 좁아졌기 때문입니다.

### 3. 해결 방안 (Resolution)
*   **통로 간격(Gap) 최소치 보장 알고리즘 도입**:
    *   깔때기 출구의 실제 폭(`_exitW`)을 계산한 후, 런치패드들의 총 너비가 출구 폭에서 최소 간격 22px(구슬 지름의 약 2배)을 보장할 수 있는지 검사합니다.
    *   공간이 부족할 경우, 초과 비율(`_sc`)만큼 런치패드의 크기(`_lpWL, _lpWC, _lpWR`)를 동적으로 축소(Scaling)하여, 모바일 디바이스에서도 공이 원활하게 골인선으로 통과할 수 있도록 물리 환경을 반응형으로 자동 보정했습니다.
    *   추가로 포탈 반경(`PORTAL_R`) 등 고정 크기를 가지던 다른 기믹들에도 `BOARD_XSCALE` 적용을 일괄 검수 및 적용하였습니다.
